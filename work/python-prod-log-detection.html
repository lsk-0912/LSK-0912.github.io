Python 生产服务日志检测实践

2026年11月4日 工作

做 Python / AI 应用服务时，日志往往是最先能回答「线上出了什么」的数据源。本文整理一套可落地的做法：先把日志写成可检索的结构化字段，再做异常检测与告警，最后按规模选择采集和检索工具。检测在这里侧重异常发现，而不是单纯把日志存起来。

为什么要做生产日志检测

生产环境里，用户先于你发现问题的成本很高。日志检测的目标是把「有人反馈了才去翻机器」改成「阈值触发后带着上下文去定位」。

  • 故障早发现：错误率、超时、连接失败会先于工单出现。早几分钟发现，往往能把影响从整段高峰缩到一次发布回滚窗口。
  • SLA 可核对：可用性、P99 延迟、失败率需要可复算的证据。日志是请求级事实，指标是聚合视图，两者要对得上。
  • 安全审计：登录失败突增、越权接口、异常 Token 使用，通常先从访问日志和鉴权日志露头。没有结构化字段，事后追查会变成全文检索碰运气。
  • 容量与错误率：QPS 爬升、慢查询变多、下游超时变密，是扩容或降级的信号。只看 CPU 而不看错误构成，很容易把容量问题和代码缺陷混在一起。

对 AI 应用尤其明显：模型调用超时、token 超限、工具调用失败往往不是进程崩溃，而是业务错误码缓慢恶化。没有日志侧检测，仪表盘上的「服务还活着」会掩盖「功能已经不可用」。

日志规范建议

检测规则能写多准，取决于日志字段稳不稳。建议默认输出 JSON 一行一条，避免多行 Traceback 把采集器拆散；异常堆栈放进独立字段，而不是直接打印到标准输出后指望人工眼扫。

必填字段

每条业务日志至少带上下面这些键，名称固定，不要今天写 traceId、明天写 trace_id：

  • timestamp：ISO 8601，带时区，例如 2026-11-04T10:15:30+08:00。
  • level：DEBUG / INFO / WARNING / ERROR / CRITICAL。
  • service：服务名，和部署单元一致，便于多服务共用一个索引。
  • trace_id：一次分布式调用的追踪标识，由网关或 OpenTelemetry 注入。
  • request_id：单次 HTTP / RPC 请求标识，方便只捞这一跳。
  • message：给人读的短句，不要把整段 JSON 再塞进这个字段。

建议再补 env、host、path、status、latency_ms、error_code。AI 服务还可以加 model、provider、token_in / token_out，但不要记录完整 prompt 或用户原文。

级别约定

  • INFO：请求开始/结束、关键业务状态变更。高频路径控制字段，不要每个循环都打。
  • WARNING：可重试的下游抖动、降级生效、接近配额。它表示「还能扛，但要盯」。
  • ERROR：这次请求失败，调用方已经或即将感知到。必须带 error_code 和异常类型。
  • CRITICAL：进程无法继续提供核心能力，例如配置缺失、主存储不可达、证书过期。

不要把预期内的 404、参数校验失败打成 ERROR，否则错误率告警会被噪声淹没。业务失败用稳定的 error_code，系统失败才升到 ERROR。

敏感信息脱敏

日志会进采集器、对象存储和值班群。Token、手机号、身份证必须在写出前处理，而不是指望检索平台事后打码。

import re

TOKEN_RE = re.compile(r"(?i)(bearer\s+|token=)[A-Za-z0-9._\-]+")
PHONE_RE = re.compile(r"1[3-9]\d{9}")
ID_CARD_RE = re.compile(r"\b\d{17}[\dXx]\b")

def redact(text: str) -> str:
    text = TOKEN_RE.sub(r"\1***", text)
    text = PHONE_RE.sub(lambda m: m.group(0)[:3] + "****" + m.group(0)[-4:], text)
    text = ID_CARD_RE.sub(lambda m: m.group(0)[:4] + "**********" + m.group(0)[-4:], text)
    return text

更稳妥的做法是白名单字段：只序列化允许输出的键。Authorization 头、Cookie、私钥、完整 prompt 直接丢弃。脱敏规则要覆盖 message、异常字符串和额外 context，漏一个字段就等于没做。

Python 采集与写出

标准库 logging 足够支撑大多数服务。需要稳定 JSON 字段时，用 structlog 或 python-json-logger。三者可以并存：业务代码走 structlog，第三方库仍由标准 logging 接管。

结构化 logger 配置片段

下面这段把标准 logging 配成 JSON 行输出，并强制带上服务名。生产里优先打到 stdout，交给 sidecar / Agent 采集，而不是让每个 worker 自己轮转文件。

import json
import logging
import os
from datetime import datetime, timezone

class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "timestamp": datetime.now(timezone.utc).isoformat(),
            "level": record.levelname,
            "service": os.getenv("SERVICE_NAME", "demo-api"),
            "trace_id": getattr(record, "trace_id", "-"),
            "request_id": getattr(record, "request_id", "-"),
            "message": record.getMessage(),
            "logger": record.name,
        }
        if record.exc_info:
            payload["exc_info"] = self.formatException(record.exc_info)
        return json.dumps(payload, ensure_ascii=False)

def setup_logging() -> logging.Logger:
    handler = logging.StreamHandler()
    handler.setFormatter(JsonFormatter())
    root = logging.getLogger()
    root.handlers.clear()
    root.addHandler(handler)
    root.setLevel(logging.INFO)
    return logging.getLogger("app")

logger = setup_logging()
logger.info(
    "模型调用完成",
    extra={"trace_id": "tr_8f2", "request_id": "req_19c"},
)

structlog 的常见接法

structlog 适合把 trace_id 绑到上下文，避免每个调用都传 extra。官方文档见 structlog.org。

import structlog

structlog.configure(
    processors=[
        structlog.contextvars.merge_contextvars,
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.JSONRenderer(ensure_ascii=False),
    ]
)
log = structlog.get_logger("app")

# 在中间件里绑定一次，后续自动带上
structlog.contextvars.bind_contextvars(
    service="demo-api",
    trace_id="tr_8f2",
    request_id="req_19c",
)
log.warning("下游超时，准备重试", provider="llm-a", latency_ms=3200)

多进程 / 多 worker 注意

Gunicorn 的 sync / gthread worker、Uvicorn 的多进程模式，都是多个解释器各写各的。直接用 FileHandler 或 TimedRotatingFileHandler 指向同一文件，会出现交叉写入、轮转抢锁、部分行截断。更稳的选择：

  • 每个进程只写 stdout / stderr，由进程管理器或 Filebeat / Fluent Bit 采集。
  • 必须写文件时，按 worker_id 或 PID 拆文件，或者经 QueueHandler + 独立 listener 进程串行落盘。
  • 不要在 preload 之后再改 root logger 的可变全局状态，子进程会继承半初始化的 handler。

异步服务注意

asyncio / FastAPI 里，logging 的 emit 默认是同步的。把日志写到慢磁盘或远端 HTTP，会堵住事件循环。异步服务应把 handler 留在内存队列或 stdout；重试、告警投递放到后台任务。也不要在 access_log 里同步序列化超大请求体。Uvicorn 的访问日志和业务 JSON 日志建议分开，避免一种格式污染另一种解析。

常见检测手段

「检测」不是把所有 ERROR 推到群里，而是用少量可行动的规则覆盖高价值故障模式。

错误率、超时、5xx、业务错误码突增

以请求总数为分母。只看 ERROR 绝对数，会在流量高峰误报、在低峰漏报。建议同时盯：

  • HTTP 5xx 占比、网关超时占比。
  • 下游超时（LLM、向量库、对象存储）按 provider 分组。
  • 稳定业务错误码，例如 MODEL_OVERLOADED、QUOTA_EXCEEDED 在 5 到 15 分钟窗口内的倍数变化。

突增检测比静态阈值更抗流量波动：当前窗口对比前一个窗口或同比同时段。静态阈值适合「5xx 超过 2% 持续 5 分钟」这种 SLA 红线。

关键字 / 正则匹配

结构化日志还没铺开时，正则仍是兜底。常见高信号词：ERROR、Traceback、OOM、MemoryError、Connection refused、Too many open files、SSL: CERTIFICATE_VERIFY_FAILED。对 Python 服务再加 CancelledError 刷屏、Event loop is closed。

正则适合「进程已经在喊救命」的情况，不适合统计失败率。堆栈中的 Error 子串很容易误匹配，匹配后最好再按 level 或异常类型过滤。

指标衍生

从日志聚合出 QPS、P99、failed / total，可以补上 APM 还没覆盖的内部路径。做法是在请求结束日志里带 latency_ms 和 status，采集端按时间桶计算。注意采样：DEBUG 被关掉后，如果结束日志也没了，衍生指标会一起失真。请求级 INFO 应视为指标源，而不是可随意关闭的调试输出。

健康检查日志与探活区分

负载均衡和 K8s 探活会打出大量 GET /health 或 GET /ready。这些请求不应计入业务 QPS，也不应触发「流量骤降」告警。处理方式：

  • 探活接口单独 logger，或字段 route_kind=health。
  • 访问日志过滤器直接丢弃探活成功记录，失败仍保留。
  • 告警查询默认 path != /health。

探活失败本身是信号，但要和业务 5xx 分开告警，否则值班会分不清是实例挂了还是某个模型路由挂了。

轻量自建检测示例

小规模单机服务、或平台告警还没接上时，可以用一个短脚本做兜底：读 stdin / 轮询文件 → 解析 JSON 或走正则 → 在滑动窗口里计数 → 超阈值后调用 webhook。生产环境仍应优先接现成平台；自建脚本没有持久化、没有抑制、也没有值班排班，只适合过渡。

下面的脚本从标准输入读 JSON 行，统计 5 分钟窗口内的 ERROR，超过阈值就调用一个本地占位函数。Webhook 地址从环境变量读取，代码里不要写真实 URL 或密钥。

#!/usr/bin/env python3
"""从 stdin 读取 JSON 日志，窗口内 ERROR 超阈值则告警。"""

import json
import os
import sys
import time
from collections import deque

WINDOW_SEC = 300
ERROR_THRESHOLD = 20
# 仅作占位，真实地址放环境变量，例如 DINGTALK_WEBHOOK
WEBHOOK_URL = os.getenv("ALERT_WEBHOOK_URL", "")

recent_errors = deque()


def notify(count: int, sample: dict) -> None:
    title = f"[alert] {WINDOW_SEC}s 内 ERROR={count}"
    body = {
        "title": title,
        "service": sample.get("service"),
        "trace_id": sample.get("trace_id"),
        "message": sample.get("message"),
    }
    if not WEBHOOK_URL:
        print("ALERT_STUB", json.dumps(body, ensure_ascii=False))
        return
    # 这里接钉钉 / 飞书自定义机器人即可，注意加签与频率限制
    print("ALERT_WOULD_POST", WEBHOOK_URL.split("?")[0], title)


def ingest(line: str, now: float) -> None:
    try:
        item = json.loads(line)
    except json.JSONDecodeError:
        if "Traceback" in line or "Connection refused" in line:
            item = {"level": "ERROR", "message": line[:200], "service": "unknown"}
        else:
            return

    if str(item.get("level", "")).upper() != "ERROR":
        return

    recent_errors.append((now, item))
    while recent_errors and now - recent_errors[0][0] > WINDOW_SEC:
        recent_errors.popleft()

    if len(recent_errors) == ERROR_THRESHOLD:
        notify(len(recent_errors), item)


def main() -> None:
    for raw in sys.stdin:
        ingest(raw.strip(), time.time())


if __name__ == "__main__":
    main()

本地可以这样试：tail -F /var/log/app.json | python detect.py。加文件轮询时用 inode + offset，避免 logrotate 后从头重放；多进程拆文件就要对每个文件各跟一条。告警务必做冷却，例如同一规则 10 分钟只发一次，否则窗口滑动会连打。

自建脚本适合一台机器、一个服务、一种失败模式。服务一多，就要把解析、计数、通知拆开，最终会重造一套简陋监控。到了这个临界点，应换成 Loki / Elasticsearch / 云监控，而不是继续加正则。

好用的工具清单

按职责选型，避免「一个进程既采集又告警又画图」。下面只列常见、文档公开的工具，链接指向官网或官方文档。

采集 / Agent

  • Filebeat：收文件、stdout 和部分云日志，送进 Elasticsearch 或 Logstash，配置面相对小。
  • Fluent Bit：占用低，适合 sidecar；Lua / 过滤器可以做初步脱敏和字段改名。
  • Vector：用配置语言做路由和变换，适合把同一份日志同时送给检索和指标后端。
  • Promtail：Loki 的传统 Agent，按标签抓文件。新项目也可以评估 Grafana Alloy，但现有 Loki 栈里 Promtail 仍很常见。

存储 / 检索

  • ELK（Elasticsearch + Kibana）：全文检索和灵活聚合强，运维成本也高。产品入口见 Elasticsearch。
  • OpenSearch：检索体验接近 ES，适合已经熟悉 Kibana 查询、又希望走开源发行的团队。
  • Loki + Grafana：按标签索引，存储更便宜，查询习惯接近 PromQL。标签要克制，高基数 trace_id 不要当 label。
  • Graylog：自带告警和流规则，中小团队想少拼组件时可以看。

APM / 可观测

  • OpenTelemetry Python SDK：统一 trace / metrics / logs 的上下文。先把 trace_id 打进日志，收益通常大于先上全量自动埋点。
  • Sentry Python：错误聚合、发布版本对照、现场变量。它补的是「这类异常出现过多少次」，不能替代访问日志。
  • Datadog、New Relic 等商业方案把 APM、日志、基础设施放在同一套查询里，适合已经在为值班效率付钱的团队；自建栈则用 OTel 导出，避免业务代码绑死厂商 SDK。

本地 / 运维

  • jq：切 JSON 字段、算粗计数，排障时比把日志贴进编辑器快。
  • lnav：多文件时间线、SQL 式过滤，看轮转后的一堆 .log.1 很方便。
  • multitail：同时跟多个服务的文本日志；和 grep / ripgrep 搭配做关键字兜底。
  • journalctl：服务由 systemd 托管时，先确认应用有没有把日志送到 journal，再决定还要不要 Filebeat 扫文件。

Python 库

  • structlog：上下文绑定和处理器链清晰，适合中间件注入 trace_id。
  • python-json-logger：在现有 logging 上换成 JSON formatter，改动面小。
  • logging.handlers：单进程文件轮转用 TimedRotatingFileHandler；多进程不要共用一个文件 handler。
  • watchdog：监听目录里新日志或轮转事件，适合本地检测脚本，不适合当作生产采集器。
  • tenacity：重试时用 before_sleep 打 WARNING，带上尝试次数和下游名称，避免重试默默耗尽预算。

落地建议

  1. 先规范格式：统一 JSON 字段和级别，把探活、访问、业务错误分开。格式不稳，后面的采集和告警都会反复返工。
  2. 再接采集：stdout → Agent → 检索平台。应用进程尽量不直接打远程 HTTP 日志。
  3. 最后写告警：每条告警对应一个可执行动作，例如回滚、扩容、切供应商、查某条 trace_id。没有动作的告警不要建。
  4. 防风暴：同一规则做冷却和聚合；发布窗口允许临时静音；避免「一条 Traceback 拆成 40 条群消息」。
  5. 保留串联字段：trace_id 从网关传到 worker、工具调用和模型客户端。排障路径应是告警 → 一条 trace → 相关日志和 span，而不是按关键字在全库碰运气。

对 AI 应用，额外建议把「模型成功但结果不可用」做成业务错误码，而不是只打一句 INFO 生成完成。内容安全拒绝、空结果、工具调用失败都要能被窗口计数看到。
